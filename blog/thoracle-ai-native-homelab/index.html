Thoracle: An AI-native homelab platform

Nov 26, 202619 min read

On this page

    Goal

    Thoracle is my infrastructure playground: an environment I fully control, built the way larger organizations deploy their services. It has three jobs:

    • Test bench. Plug in a new service or app to try it, without asking anyone.
    • Home for my dev work. My own projects are built and run here.
    • Bleeding edge. Run the newest infrastructure ideas, not only the ones an employer already uses.

    Work experience only teaches the infrastructure an organization already has. Owning the whole stack is how I find better ways to run it.

    What Thoracle Is

    Thoracle is a homelab project that simulates how enterprise AI platforms work, scaled down to a few users on consumer equipment. Each layer a large company would run, from the front door to the secrets store, has a homelab stand-in.

    Because it runs at home, chats, pictures and documents stay fully local. A local model costs nothing per request, and no provider sees what you ask it. The software is free, and the cloud spend fits inside a $40 monthly credit.

    It does not make a model faster or smarter, and a cluster does not survive a power cut or a dead router.

    Current State

    Thoracle runs today on three machines and Cloudflare. One always-on NUC runs everything people touch: the front door, the apps, the model gateway and the database. Two GPU machines run the private models, and Cloudflare lets people in from outside.

    It works, but the NUC is a single point of failure. If it stops, chat, the gateway, the agent and home lookups stop with it.

    Future State

    Thoracle's future shape is one K3s cluster in place of the single NUC. Three small PCs run it as managers, and the NUC and the 5060 Ti machine join as workers. The RTX 4090 workstation stays outside and lends its GPU through Rhystic Study, my routing filter, when it is on.

    Around that core it adds a secrets store, monitoring, a job queue and an off-site backup copy, so no one machine can take the platform down.

    Read it against the current-state map above: what ran on the NUC now spreads across the cluster, and gold marks what is new. People still come in through Cloudflare, and a copy of the backups now leaves the house.

    The machines this shape needs come next, then what the change makes possible.

    Hardware specifications

    What This Change Enables

    Always-on core. Thoracle keeps running when a machine dies. Today one NUC carries chat, the gateway, the agent and home lookups, so its failure stops all four. Three small PCs run as one K3s cluster instead, and when one fails, Kubernetes restarts its services on the other two.

    GPU use. The GPUs can serve more than Thoracle. The 5060 Ti machine joins the cluster as a GPU worker, so its cards can be lent to another project from git and handed back, without two workloads fighting over a card. The workstation stays outside on Compose, and Rhystic Study still sends it work through its own llama-swap when it is on.

    Data. A dead machine no longer means a restore. Today PostgreSQL lives only on the NUC. In the cluster a live replica runs on a second PC and takes over by itself.

    Backups. Backups survive losing the machine that made them. Today the nightly copy sits on the NUC's own disk. The future state keeps three copies: on the cluster, on the 5060 Ti machine's spare disk, and encrypted in Google Cloud.

    Slow jobs. Video and music jobs can run for minutes without being lost. Today a picture request holds the line until it is done, so a restart loses it. A Celery queue in Valkey gives each job a ticket, and the job waits until a GPU is free or the workstation is switched on.

    Secrets. Each app sees only its own keys. Today every key sits in a hand-edited .env on each machine. OpenBao holds them in one place and hands each app only what it needs.

    Watching. I hear about a problem before anyone notices it. Today there are Portal dots and one Cloudflare email. Uptime Kuma, Prometheus and Grafana add alerts to my phone and charts of every machine, and LiteLLM's log keeps a record of every request.

    Tools. Every app uses one list of tools. Today each app wires up its own. LiteLLM becomes the tool gateway, so a tool added once shows up in Open WebUI and Hermes alike.

    Cloudflare setup. The edge can be rebuilt from files, not from memory. Today it is six dashboard steps done by hand. OpenTofu writes those steps as files that are reviewed like code and applied the same way every time.

    The last gain is practice: Kubernetes, infrastructure as code, a secrets store, a job queue and monitoring each run for real, the way an enterprise platform runs them.

    Custom Engineering

    These are the parts I built myself. Off-the-shelf equivalents exist for some of them, but they are made for data-centre hardware, for models that stay loaded, and for teams that run each tool on its own. Thoracle runs on a few consumer machines that swap models in and out and get switched off, and it needs its pieces to work as one system. Where the available tools did not fit that shape, I built the part that did.

    Most of this carries over to the future state unchanged. Only the parts that run the core today would be rewritten for the cluster.

    Command Tower: Thoracle's dashboard

    Command Tower shows the state of all of Thoracle: every node, the models loaded on each GPU, the job queue, the gateway's day and the latest alerts. For detail, it links out to Grafana, Langfuse and the other tools. Equivalents exist: Backstage is the usual enterprise portal, and Homepage or Homarr fill the same role in homelabs. I grew the portal I already had instead, because Thoracle's own signals, such as the models loaded on each card and the job queue, would need custom plugins in any of them.

    Rhystic Study: A model-aware router

    Rhystic Study sits inside LiteLLM and decides which GPU machine answers each local request. LiteLLM alone cannot see which machine has a model loaded, and a wrong pick costs up to two minutes of loading, so Rhystic Study asks each machine first and keeps a chat on the machine that holds its context. Equivalents exist: NVIDIA Dynamo, llm-d and the Kubernetes Gateway API inference extension route requests the same way. They assume models stay loaded on data-centre GPUs under Kubernetes, not models swapped in and out by llama-swap on consumer cards, so I built my own.

    Worldly Tutor: ComfyUI without ComfyUI

    ComfyUI is powerful but intimidating: every picture is a graph of nodes to wire and settings to tune. Ready-made workflows help, yet someone still has to open one and fill in the right boxes. Worldly Tutor closes that gap. You describe the picture in chat, and it fills in the ComfyUI workflow for you. You still choose which workflow to use, but that is a far smaller ask than learning to drive one.

    Today it lives in Open WebUI as a custom tool. The plan is to serve it through LiteLLM's MCP gateway, so Hermes and any other app can call it with their own key, and to let it run community-supported ComfyUI workflows.

    Every app reaches Worldly Tutor through the same gateway with its own key, and the workflow library grows to include community-supported ComfyUI workflows.

    Services

    Thoracle is built from about two dozen services, almost all open source. They run from the bottom up: the platform everything sits on, then the front door, the apps people open, and the layers that keep those apps fast, safe and watched. A tag after each name says whether it runs today, is new in the future state, or is planned.

    Platform

    The platform is what everything runs on and how it changes. This is where the rebuild happens.

    K3s cluster new

    K3s is the foundation the future state stands on. It is Kubernetes in a small package, so three small PCs are run as one pool instead of three separate machines. When one PC dies, its services restart on the other two, which ends the NUC's role as the single point of failure. I picked K3s over full Kubernetes because it fits on consumer hardware yet uses the same commands and files as an enterprise cluster. Every always-on service below runs on it, and updates roll through one PC at a time while everything stays up. It does not move data by itself; the data stores further down do that.

    Docker Compose have today, shrinks

    Compose keeps running the RTX 4090 workstation and the dev copy, along with the deploy scripts that already work. The workstation stays outside the cluster because it is a Windows machine that gets switched off, and Rhystic Study still reaches it through its own llama-swap when it is on. The 5060 Ti machine leaves Compose and joins the cluster as a GPU worker.

    Argo CD new

    Nothing reaches prod except from git, and Argo CD carries that rule onto the cluster. It runs inside the cluster, watches the repo and changes the cluster to match, so my go-ahead becomes the merge. Its web UI shows each app's sync state, which Command Tower can link to for detail. It replaces custom shell scripts for the core, while the workstation keeps its deploy scripts. Only its bootstrap lives outside: one command that installs it on a fresh cluster and lets it restore everything else from the repo.

    OpenTofu new

    OpenTofu turns setup done by clicking into files. The Cloudflare edge, Google Cloud and GitHub's repository rules become code that shows a plan before it applies, the same dry-run habit Thoracle uses everywhere. The edge can then be rebuilt from files rather than memory, and a hand edit in a dashboard shows up as a difference. It is the open continuation of Terraform.

    Sandbox new

    The sandbox is where a new service gets tried without risking what my users rely on. By default a try-out runs in a fenced-off namespace, an area of the cluster with its own memory and CPU cap that cannot reach anyone's data. A test of the platform itself, such as a new Argo CD or Longhorn version, gets a virtual cluster (vcluster): a whole K3s of its own inside the real one, free to break. Anything that needs a whole machine, such as another operating system or a Docker Compose stack, gets a VM on the cluster through KubeVirt.

    Front door

    Three services make one address work from the couch or from another country. All three run today.

    Cloudflare Tunnel and Access have today, grows

    The tunnel is the only way in from outside. A connector dials out from the house to Cloudflare, so no router port is ever open, and Access puts an email-code gate in front of the portal and admin pages. In the future state two connectors run on different PCs, so losing one does not cut the way in.

    Caddy have today

    Caddy is the doorman inside the house. It sends each web address to the right app and gives home devices a real certificate, so nobody sees a browser warning. On the cluster two copies stand behind one address that follows a live PC. Whether Caddy stays or K3s's built-in front door takes over is still open.

    Pi-hole have today

    Pi-hole answers “where is the chat?” for every device at home and points it straight at the stack. That is faster than going out through Cloudflare and keeps working when the internet is down.

    Apps

    Only four things are ever opened by a person. Everything else in Thoracle exists to keep these four fast, private and available.

    Open WebUI have today, grows

    Open WebUI is the chat my users know. It holds their accounts and chats, the picture tools and the entry that summons Hermes. In the future state two copies run on different PCs, sharing files through common storage and live state through Valkey, so a chat survives a PC being replaced or an update rolling out.

    Hermes Agent have today

    Hermes is the agent that does the work: it runs commands and reads and writes the folders I allow. It gains the most from the tool gateway, since every tool added there reaches it the same day. Its fence today is a firewall rule tied to one machine and address, so it needs a new design on the cluster, and that decision is still open.

    Command Tower have today, grows

    Command Tower is the operator's front page: which machines are on, which model is loaded where, the job queue and the latest alerts. It shows the headline and links out to Grafana and Langfuse for detail. Custom Engineering covers why I built it.

    Samba have today, grows

    A shared drive gives my users one place for files, opened like any network drive from File Explorer or Finder. Samba serves it, and its files sit on a Longhorn drive, so when a PC dies it restarts on another with its files intact.

    Gateways

    A gateway makes many things look like one, so new parts can be added behind it without touching what is in front. That idea is why Thoracle can grow.

    LiteLLM have today, grows

    LiteLLM puts every model, local or cloud, behind one door. Apps never hold a provider's key; each carries a LiteLLM key that can be limited or revoked, and a model added once appears everywhere. Rhystic Study lives inside it and picks the GPU machine for each local request. In the future state two copies share their state through Valkey, and LiteLLM switches on features it already has: a tool gateway, a key and budget per person, and a log of every request.

    MCP Tool Gateway (via LiteLLM) new

    Today a tool belongs to one app, so Hermes cannot use the picture tools that live in Open WebUI. The tool gateway puts every tool server behind one address, limits each key to its own tools and records every call. A tool is added once and works everywhere, which is how Worldly Tutor reaches Hermes. It also widens what Hermes can reach, so each tool it gets is my call.

    SearXNG new

    A model that cannot search answers from memory. Web search puts one endpoint in front of many search engines, so a chat model can look things up and show its sources. It becomes one more tool behind the gateway, running on the cluster.

    Model serving and jobs

    The GPU machines hold the private models and change least. The 5060 Ti machine joins the cluster as a GPU worker, the workstation stays on Compose, and the new job queue feeds both work that takes minutes rather than seconds.

    llama-swap have today

    The cards cannot hold every model at once, so llama-swap is the referee on each GPU machine. It loads and unloads models on demand, lets a chat evict a picture model, and refuses a picture rather than evict a chat. Rhystic Study and Celery's workers both send work through it, so each machine keeps a single referee.

    Strata have today

    Strata is the chat engine that runs Flash-Next, the long-context model, on both machines. It makes long chats and long agent tasks possible on my own cards, privately and at no cost per request.

    ComfyUI have today

    ComfyUI makes the pictures. Worldly Tutor translates a plain request into the right workflow for it, so pictures travel through the same gateway as chat and LiteLLM can place them on whichever machine is free. Video and music will use the same engine later, arriving through the job queue because they run for minutes.

    Celery new

    A video takes minutes, and holding a request open that long breaks things: a restart loses the job, and a workstation that is off cannot be waited for. Celery fixes this with a ticket. A tool hands in the job, the job waits in Valkey, and a worker on a GPU machine takes it when a card is free, so “make this clip when the 4090 is on” becomes a normal request. It sits beside Rhystic Study rather than replacing it: live chat streams word by word, slow jobs wait in line. A queue inside PostgreSQL would do for six people; Celery is here to scale.

    Data

    A cluster moves a program to a surviving PC, but not the program's data. These services make the data follow.

    PostgreSQL have today, grows

    PostgreSQL holds everything worth restoring: accounts, chats and keys. Today it lives only on the NUC, so a dead NUC means a restore. In the cluster a live replica runs on a second PC and takes over by itself, managed by a Kubernetes add-on (CloudNativePG).

    Valkey new

    Valkey is the system's whiteboard, a fast in-memory store for small, short-lived values. It is Celery's waiting room, Rhystic Study's memory, Langfuse's queue, and the shared state that lets two copies of LiteLLM or Open WebUI run side by side. Without it no app can run as two copies, so it is what makes the redundancy above real.

    Longhorn, Garage new

    Shared storage makes “any PC can fail” true for files, not just programs. Without it, Open WebUI's uploads and pictures stay on the PC that died. It comes in two kinds, and each app uses the one it needs. Shared disks (Longhorn) give an app a drive that is copied to other PCs as it writes, for apps that save to a folder. A file store (Garage) takes whole files and hands them back by name, S3-style, for apps like Langfuse that need one. Garage replaces MinIO, whose free edition was retired.

    ClickHouse new, comes with Langfuse

    ClickHouse answers sums and averages over millions of rows at once, such as average reply time per model this month. Only Langfuse needs it, to hold traces, and it is Langfuse's hungriest part at an 8 GB memory minimum.

    Watching

    Today I learn about a problem by running into it. These services tell me first, show you where, and keep a record of what happened.

    Uptime Kuma new

    Uptime Kuma checks every service about once a minute and sends an alert to my phone when one stops answering. It also expects a “done” signal from the nightly backup and speaks up when none arrives. One copy runs on the cluster and a tiny one on a free Google Cloud machine, the only thing that can tell me the whole house is offline.

    Prometheus and Grafana new

    An alert says something broke; Prometheus says what was happening before it did. It collects numbers from every machine every few seconds, such as GPU memory, disk space and request counts, and keeps their history. Grafana turns those numbers into charts and holds the alert rules, with its dashboards kept in git. Together they turn surprises into warnings, like a backup disk that will be full in three weeks.

    LiteLLM request log built in, off by default

    Machines are only half the story; the other half is what people asked and what came back. LiteLLM can store each request's prompt, reply, time and token count, grouped by chat, with no new service to run.

    Langfuse new, optional

    Langfuse shows an agent task or a picture loop as a tree of steps and compares runs, so “why was that slow?” has an answer. It is the heaviest tool here, needing ClickHouse, Valkey, a file store and PostgreSQL, about 25 GB of memory in all. It comes last, and only if LiteLLM's own log falls short.

    Secrets and cloud

    Thoracle stays private and self-hosted. Secrets move into one guarded place, and the cloud is used only for what three machines in one house cannot do.

    OpenBao new

    OpenBao holds every key in one guarded service and hands each app only its own, replacing a hand-edited .env on each machine. A shared key is changed once, every read is on record, and short-lived passwords expire within an hour, so a leaked one is soon worthless. A small helper fetches each app's secrets at start-up, so services move over one at a time without code changes. It is the open continuation of HashiCorp Vault. After a power cut it comes up locked, so automatic unlocking has to be designed in.

    Google Cloud new, paid

    Google Cloud does the three things a house cannot: keep a backup copy somewhere else, watch the house from outside, and stand in for the workstation's speech models when it is off. It also gives a place to practice Kubernetes with OpenTofu used for real.

    Anthropic API have today

    The strongest models are ones Thoracle does not run. Anthropic's are reached only through LiteLLM, so chat keeps working with both GPU machines off. Adding another provider is a few lines in one file and changes no app.

    Tenants

    In an enterprise environment, a platform team runs the platform, and each product team's apps run on it as tenants, each with its own space, limits and deploys. Thoracle would host mine the same way:

    manavault-ph is a storefront for Magic: The Gathering singles, cards sold one at a time. Shopify and WooCommerce cannot handle them. One card comes in many printings and finishes, every copy has its own condition, and prices move with demand. Selling other people's cards on consignment adds another layer, so I built my own store.

    gitaxian-probe exists because building manavault-ph uncovered a pricing problem. Philippine sellers price cards from US market data, but the cards for sale here are not the ones for sale overseas, so those prices are often wrong. gitaxian-probe reads the local market to measure real local supply and demand, and its data sets manavault-ph's prices.

    Closing thoughts

    I started Thoracle to learn how enterprises run their platforms. Building my own showed me where their tools stop fitting consumer hardware, and that is where the interesting work is. Rhystic Study and Worldly Tutor exist because nothing off the shelf did the job.

    The future state is the next round of the same lesson. A cluster, a secrets store, a job queue and real monitoring each teach something a single machine cannot, and every one of them runs on hardware I own and am free to break.

    If you are building your own, here is what I would tell you:

    • Put a gateway in front of your models first. With one door for every model, apps never hold a provider's key, and a new model shows up everywhere at once.
    • Use off-the-shelf tools until they stop fitting. Build your own part only where they assume hardware or habits you do not have.
    • Make every change go through git. A dry run before each change turns a homelab from something you remember into something you can rebuild.
    • A copy is not a backup. Replication copies a mistake to every machine at once; only a backup undoes a bad change.

    None of this is finished, and that is the point. I will write up each layer as I build it.
